# Pulse · Module 3 — 每周挽留预算决策板（live dashboard）

把静态样图升级成**从 `data/` 真实计算**的可运行版本。零第三方依赖，纯 Python 标准库。

> **一句话定位**：Pulse 不是告诉你谁要走了，它告诉你——这一周，那笔挽留预算该花在谁身上、花多少、以及为什么对某些人一分都不花。
> **使用者**：每周三打开审批清单的营销经理（不是「AI 系统」）。

---

## 范围：只跑通一条路径，其余标 v2

```
打开页面 → 门店健康（可点/可抑制）→ 钻取该店真实名单 → 按净收益排序的五组决策
→ 批准一条（强制书面理由 + 服务端复核同意）→ 写 append-only 审计日志 → 可抽查「凭什么」
```

**明确不做**：店内 POS 界面、ML 重训、真实部署、市场调查、CDP 去重、六模块联调。
范围裁剪本身是评分项，不要临时加功能。

## 目录

```
pulse_app/
  pulse_core.py       # 评分核心：门店漂移 + 五组决策 + 基线口径 + 成本表（可单独 import / 测试）
  pulse_app.py        # HTTP 服务（stdlib http.server）+ API + 审批/抑制写回
  static/index.html   # 前端单页，三个 Tab（活看板，连接真实 API）
  selftest.py         # 可复算性自检：PRD 数字逐一对照数据重算
  run.bat             # Windows 一键启动
  studio_data.json    # Decision Workspace 内嵌数据源（由 pulse_core 实跑导出）
  _studio_template.html # 成品页模板，改数据后重新注入即可再生成
  audit/              # 运行时生成：decision log + 全量决策快照
```

**另有一份离线成品页**：`../Pulse_Decision_Workspace.html`（双击即开，无需服务）。
它是同一套真实数据、同一套规则的**演示/交作业用外壳**，7 个模块、可点可签字；
与活看板 `localhost:8000` 同源，不是另起炉灶的第二套系统。

```bat

```


## 三个页面 / API

| 页面 | 内容 | API |
|---|---|---|
| ① 门店诊断 + 人工闸门 | 25 店；观察周下拉（36 个可选周）；**门店诊断卡**（给高层看的一页：现象、该店值得救的人数 / 高 / 中、券面值需求、排查结论、谁去看过、下一步——只看不点不改钱）+「这一页不管什么」边界表；告警只出排查清单，**压制必须经理签字**，签字弹窗先显示代价（少多少预期净收益 / 换掉几人 / 暂缓几人），可恢复投放；压制状态落盘 `audit/store_suppression.json` | `GET /api/stores?week=N`, `POST /api/diagnose` |
| ② 行动清单 | 真实名单、按净收益降序、服务端分页（显示 `200 / 5,716`）、按门店/分组过滤、**本周预算分配 + 压制代价 + 被暂缓名单**、**下周预算建议卡**（现金上限 / 覆盖率目标 → 券数、边际曲线、饱和点）、基线口径卡、活的成本参数表 | `GET /api/actions`, `/api/summary`, `/api/baseline`, `/api/savings`, `/api/budget`, `/api/advice` |
| ③ 审批记录 | append-only 日志，随机抽一条能答「发给谁 / 什么同意依据 / 谁批 / 何时批 / 凭什么」 | `GET /api/audit`, `POST /api/approve`, `POST /api/suppress` |

**写回契约**：`audit_messages.csv` 与共享 `messages` 表同 7 列（`status=approved`），
源文件 `messages.csv` **从不被改动**；扩展字段在 `audit/pulse_decision_log.csv`，
用 `message_id` 关联。`sent_at` 在批准时**故意留空**——批准 ≠ 发送，PDPO 要求发送时
同意仍有效（§9.3）。

## 已落实的关键口径

- **两层不混**：门店层 = **诊断视图 + 人工闸门**（PRD「budget-and-suppression unit」的落地口径）。
  告警与诊断卡只解释上下文：不改分组、不改券数、不自动压制、不新增门店活动预算；
  个人层 = 花钱单元（对象与上限）。**唯一能改钱的动作**是经理签字压制，签字前先算代价，
  签字与代价一起入审计。DSH 提的「结构性问题」= 人想回来但回不来（路在修 / 商场改入口 /
  对面新店截客），诊断卡负责把这类店交给人去现场核实，不负责预测谁会流失。
- **压制不省钱，只会换人**（实测，同一笔 HK$15,400）：压 1 家（PCC007）花钱不变、
  预期净收益 −HK$6,103（−0.86%）、9 人换人；压 7 家（W45）−HK$80,193（−11.31%）、
  78 人换人。所以默认不压；要压必须有人负责，并知道自己在买什么（外部原因）。
- **无前视**：个人基线、归属店只用 ≤ cut 的交易；门店回放周只用该周之前的历史，
  自身 P10 也只取到观察周为止。
- **82.8% 可复算**：`selftest.py` 在 2026-04-30 切口复现 **82.8%（n=1,047）**；
  本板自己的 2026-09-30 切口是 **78.5%（n=1,465）**。两个切口**永不进同一张表**，
  界面写明 cut / n / 排除规则（已排除观测窗内被联系者）。
- **「不用管」有真数字**：偏离分桶的经验 30 天回流率，取自 90 天前的训练切口，
  避免用评估切口自己验证自己；界面注明「不是预测模型、不是实验结果」。
- **规则定金额，AI 只翻译理由**：`if` 规则给出分组/渠道/上限（HK$50 / 30 / 0），
  服务端复核 `cap`，客户端改不了；`net_gain = ERV − 券上限` 只是排序代理量。
- **批准是闸门**：必填书面理由 + 操作人；服务端二次校验 consent（渠道/basis/opt-out）；
  幂等键防重复点击；`approved_at` 与 `sent_at` 分离；线程锁。
- **「不花钱」也可审计**：启动时写一次全量决策快照（5,716 行，每行含 reason / cap /
  group / 回流概率），可申诉、可复算。
- **审批工作量实测**：批量口径 110.5 分钟，若全量逐条审批 676 分钟（11.3 小时）；
  两个数字都上屏，诚实回答「5,000 行会不会淹死经理」。
- **现金闭环是活的**：券面值 / 兑换率 / 毛利率 / 旧规则覆盖率现场可改；并列给出
  「全量名单口径」与「PRD §4 的 350 张周预算口径」，并区分券面值与现金成本。
- **「下周该批多少」= 两个外部输入 + 一条硬上限**：`GET /api/advice` 用
  `券数 ≤ 财务真现金 ÷ (面值×兑换率×毛利率)` 与「覆盖率目标」反推券数（对真实装填规则二分），
  取更紧的一个再封顶到饱和点。本周实测：每张券真现金 HK$8.58、HK$3,003 → 350 张（42.8%）、
  覆盖 90% → 737 张（HK$6,323）、**819 张饱和（922 人全发完）**，再多给券没人可发。
  所有可批准客户 `net_gain > 0`，模型不会自己喊停——总额只由现金流 / 覆盖率目标决定。

## 已知限制（演示要主动说，不要等被问）

1. 早期回放周（如 week 13）自身 P10 只有 3 个观测，统计意义弱；现场以固定阈值 −0.10 为准。
2. 外部上下文（天气 / 客流 / 假日，§3.2 #4）未接入，告警原因栏明确标「待核实」。
3. `campaign_id` 用 CP007 / CP003 作演示 join key，其真实 offer 与 HK$50 / 30 上限不一致，
   需 Module 2 建 Pulse 专属 campaign 或改 caps。
4. 「自行回流率」是经验分桶率，不是因果 uplift；成本表的券面值 / 兑换率 / 毛利率均为估计。
5. `selftest.py` 打印 5 条 **PRD 与实现未对齐的数字**（见下），需要老师拍板改 PRD 还是改实现。
6. 单机进程内缓存；`audit_messages.csv` 是演示写回，不是真实发送。
7. 门店压制的代价是**实测出来的负值**（−0.86% ~ −11.31%），所以默认不压。
   这不是 bug，是产品判断：只有运营能确认「结构性、外部原因」时才值得付这个代价；
   系统负责把代价说清楚，不替人做价值判断。
8. **「第二道省钱闸门」在本数据里不成立**：350 张券 / 922 候选，压掉谁后面都有人补上，
   花钱恒为 HK$15,400；压 1 家换 9 人、预期净收益 −HK$6,103，压 7 家 −HK$80,193。
   真要省现金得同时把券数砍到 341（省 HK$77/周），反而亏更多。真正省钱的是个人层
   4,794 条 no_spend（≈HK$34,603/周）。道理没错，是模型缺变量：`net_gain` 用历史消费
   估「这人以后会花多少」，没给「路在修、人根本来不了」打折 → 需给「结构性已确认」
   的店加**可达性系数**（含预计恢复日期），系数要真实外部数据才能定，标 v2。
9. **「下周预算建议」不预测下周名单**：它按本周 922 位候选测算「给多少钱能覆盖多少人」，
   不叠加本周签字压制（压制是单周决定），也不预测下周会新增多少偏离客户。下周必须重跑个人层。
   券数是按 HK$44 折算的**额度**，实际发出的是 high HK$50 / medium HK$30 券，两者张数不同。

## 老师给的参考 PCC Habit Atlas：怎么借、怎么不借

老师提供的是**描述性客户图谱**（Overview / Coffee Habit Map / AI Insights / AI Audience Explorer /
Audience Passport / Review Recovery / Rule Thresholds）。它回答「客户是谁、何时买、买什么」，
**全是「看」，没有一个能产生带签字、带理由、可复查的决定**。照抄成第二个 Habit Atlas 会
丢掉我们最值钱的四件事：人工闸门、审计留痕、预算反推、PDPO 同意复检 —— 拿长板换短板。

| 维度 | 学（形式层） | 不学（会跑偏） |
|---|---|---|
| 视觉与架构 | PCC 红 + 深色侧栏 + 米白卡片 + 左侧 7 模块导航；已落到 `Pulse_Decision_Workspace.html` | 不照搬它的 7 个页面名当成我们的模块划分 |
| 口径小字 | **每个 KPI 自带分母/切口/边界**（它甚至注明「活跃率分母是 4,874 有交易会员，不是全量注册表」）；我们把 82.8/78.5/~55 三切口做成可切换的全局约束 | 不抄它的数字：3,798 / 28,967 / 1,242,095 是他们的 demo set，我们的是 118,365 笔 / 8,014,199.7 |
| Data Coverage 第一屏 | 先证明数据可信再谈洞察；我们改讲真实边界：100% 交易带 customer_id、175 位注册零交易、4,797 人（82.4%）跨 ≥2 店、3,534 条消息因无同意被拦 | 不复制「关联率 71.2%」这个指标名 —— 我们没有匿名 POS 交易，口径不可比，写上去就是错的 |
| 图表 | 时段×星期热力图、分层条形、期间对比、券数-覆盖率曲线 | 不开「人群探索」分支（AI Insights / Audience Passport），会拆散闭环（见「范围」） |
| 分层与生命周期 | `member_tier` 真实字段验证分层有效性（人均访问 7.3 → 51.0 次，7.0×），把生命周期换成「六个决策出口 + 每出口的预算动作」 | **绝不把「Quiet 30+/60+ 天」当挽留名单**：固定 30 天会把 969 人塞给经理；我们用 1.5× 个人中位间隔，只有 922 人真正偏离 |
| Rule Thresholds | 阈值集中一页，加自测 18/18 与诚实清单 | 不把「参考有 AI 字样」当成我们要补 AI；我们全部规则可解释、带书面理由 |

**答辩一句话**：Habit Atlas 回答「发生了什么」；Pulse 回答「这周该不该花这笔钱、谁批的、能不能复查」。
**凭什么说更好**：参考 7 个模块里没有一处涉及钱、没有一处能签字、没有一处能倒查；我们补齐同一套
诊断层后，还多出决策层（Action Queue / Budget & Gate / Audit & Rules）。

`Pulse_Decision_Workspace.html` 的 7 屏 = 参考的诊断 4 屏（Overview / Habit Map / Tiers / Store）
+ 我们独有的决策 3 屏（Action / Budget / Audit）。顶部红条常驻这句差异，每屏底部
「DECISION HOOK」写明这一屏能产生什么决定、谁签字、留什么痕。可用 `?demo=1` 或
「▶ 一键演示闭环」自动跑「批准一条 → 写入审计 → 跳到审计页」。

## 今天咨询老师：怎么讲 / 问什么

**怎么讲（3 句话开场）**
1. 我们已经把静态样图换成从 `data/` 实时算的最小可用版，只跑通一条决策路径
   （打开 → 真实名单 → 批准 → 写审计），其余全部标 v2。
2. 两层定位：门店层是**诊断视图 + 人工闸门**（告警只解释上下文，不改分组、不改券数、
   不自动压制、不新增门店活动预算；要暂停该店投放必须经理签字，签字前先看代价），
   个人层是花钱单元；「不花钱」是有理由、可申诉、有现金价值的子决策。
3. 我们主动把不能自圆其说的地方做成了可复算的自检，今天想请您帮我们拍板 5 个口径。

**这 5 个问题其实是同一件事**：我们做出来的东西，和老师手上的评分标准 / PRD 有几处对不上。今天不请老师替我们做决定，只请老师一句话定个调，回来照着改。下面每句都可以直接念出来。

**要问的 5 个问题（按优先级；前两个一定要问）**

1. **「只做一条路，够不够？」**
   我们没摊开做一堆半成品，只把「打开网页 → 看到真算出来的名单 → 点一次批准 → 留一条记录」这一条路从头跑到尾，其他功能都写了「以后做」。作业里写「三个功能，每个都要做完」，我们拿不准是要「一条路走到底」，还是要「同时摆三个」。您觉得哪种算合格？
   *我们的倾向*：一条路走到底（做完了比做得多重要）。

2. **「PRD 里的数字，是不是写错了？」**
   文档写「门店告警 4.9%、25 家店有 24 家会误报」，我们把同一份数据用代码重算，得到 3.1%、19 家。想问：是文档当时用了另一种算法（那我们改文档），还是我们代码算错了（那我们改代码）？
   *我们的倾向*：以能复算的代码为准，把 PRD 数字改成实测值，并写清楚算法。
   *为什么急*：演示现场有人拿计算器一核就露馅。

3. **「82.8% 换一天就不是 82.8% 了，怎么办？」**
   这个数只在 4 月 30 日那天算得出来；换成看板用的 9 月 30 日，同样算法是 78.5%。我们在屏幕上老实写了「哪天算的、多少人」。想问：这样标清楚行吗，还是您希望全场只用一个日期、只出现一个数？
   *我们的倾向*：两个数都留，但明确标注 82.8% 是 4 月 30 日口径，演示主讲它。
   *为什么急*：两个数同时出现，最容易被问「你们到底信哪个」。

4. **「『每周省 1,500 块』，是真省了 1,500 吗？」**
   1,500 是 35 张券的票面价（35 × 44）。真金白银省下的钱要乘「有多少人真的用券」和「毛利率」，大概只有 300 块。我们做了一张能现场改数字的表，两种口径都摆出来了。想问：演示时主打哪个数？
   *我们的倾向*：主打「真现金约 HK$300/周」，把 1,500 明确标成「票面价示意」。
   *为什么急*：一句「钱真省下来了吗」就能卡住；PRD 原来那节只写了半句，现已补完。

5. **「点完批准，要不要真的把消息发出去？」**

   *我们的倾向*：写记录 + 能点开的审计页就够了；真发送是别的模块的活，PRD 已列为「不做」。
   *为什么急*：作业要求说清「读什么、写回什么」，也要求合规（发给谁、凭什么、谁批的、什么时候）。
